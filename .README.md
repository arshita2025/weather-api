# Weather API Backend

A RESTful Weather API built using **Node.js, Express.js, PostgreSQL, and Redis**. It fetches current weather conditions and a 5-day forecast from the Visual Crossing Weather API, caches responses in Redis, and stores request history in PostgreSQL.

## Features

- **Current Weather:** Fetch current weather details for a city.
- **5-Day Forecast:** Get upcoming weather conditions and temperature ranges.
- **Redis Caching:** Cache weather responses to reduce repeated external API requests.
- **Request History:** Store weather request details in PostgreSQL.
- **Error Handling:** Handle invalid cities and external weather provider errors.
- **REST API:** Return structured JSON responses that can be tested using Postman.

## Environment Variables

Create a `.env` file in the root directory:

```env
PORT=3000
NODE_ENV=development
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/weather
REDIS_URL=redis://localhost:6379
VC_API_KEY=YOUR_VISUAL_CROSSING_API_KEY
CACHE_TTL_SECONDS=600
```

Replace the database password and API key with your own values. Ensure that the database name, credentials, and connection URLs match your setup.

**Security:** Never upload your real `.env` file or API keys to GitHub. Add `.env` to `.gitignore` and provide an `.env.example` containing placeholders instead.

## Installation and Setup

### 1. Clone the repository

```bash
git clone YOUR_REPOSITORY_URL
cd weather-api
```

Replace `YOUR_REPOSITORY_URL` with your GitHub repository URL.

### 2. Install dependencies

```bash
npm install
```

### 3. Start PostgreSQL and Redis

Start your PostgreSQL and Redis services using your Docker configuration. If your containers already exist, start them before launching the application.

Check running containers:

```bash
docker ps
```

Ensure PostgreSQL and Redis are accessible using the connection URLs in `.env`.

### 4. Start the server

Run the command configured in your `package.json`, for example:

```bash
npm start
```

If your project uses Nodemon, you can use:

```bash
npm run dev
```

On successful startup, the server initializes the database table, connects to Redis, and starts listening on the configured port.

Base URL:

```text
http://localhost:3000
```

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Check whether the API is running |
| GET | `/weather/:city` | Get current weather and a 5-day forecast |
| GET | `/history` | Retrieve recent weather request history |
| GET | `/history?limit=5` | Retrieve up to 5 recent history records |

### 1. Health Check

**Request**

```http
GET http://localhost:3000/
```

**Example response**

```json
{
  "message": "Hello, Weather API is running"
}
```

### 2. Get Weather by City

**Request**

```http
GET http://localhost:3000/weather/delhi
```

The response includes the resolved location, timezone, current weather information, and a 5-day forecast.

**Example response shape**

```json
{
  "source": "api",
  "location": "Delhi, India",
  "timezone": "Asia/Kolkata",
  "current": {
    "temp": 30,
    "feelsLike": 33,
    "humidity": 60,
    "windSpeed": 12,
    "conditions": "Partially cloudy"
  },
  "forecast": [
    {
      "date": "2026-10-15",
      "tempMax": 33,
      "tempMin": 25,
      "conditions": "Partially cloudy"
    }
  ]
}
```

*The values above are illustrative, not live weather data. The actual response depends on the API result.*

The `source` field indicates whether the response came from the external API (`api`) or Redis cache (`cache`).

### 3. Get Request History

**Request**

```http
GET http://localhost:3000/history
```

Retrieve a smaller number of records:

```http
GET http://localhost:3000/history?limit=5
```

The response contains the requested city, resolved location, data source, temperature, and request timestamp.

### 4. Invalid City

**Request**

```http
GET http://localhost:3000/weather/invalidcityxyz
```

An invalid city may return:

```json
{
  "error": "City not found"
}
```

## How Caching Works

1. The client sends a request for a city's weather.
2. The server checks Redis for a cached response.
3. If a cached response exists, the server returns it without calling the external weather API.
4. If the cache is empty, the server requests weather data from Visual Crossing.
5. The server formats the response and stores it in Redis with a configurable time-to-live (TTL).
6. The request is recorded in PostgreSQL.

The cache duration is controlled by `CACHE_TTL_SECONDS`. For example, `600` means 600 seconds, or 10 minutes.

## Database

The `weather_requests` table stores:

- `id`: Unique request record ID
- `city`: Requested city
- `resolved_location`: Location returned by the weather provider
- `source`: `api` or `cache`
- `temp`: Temperature returned for the request
- `created_at`: Timestamp of the record

The table is initialized automatically when the server starts.

## Testing with Postman

Test the following requests:

1. `GET /` — Verify that the server is running.
2. `GET /weather/delhi` — Fetch weather from the external API.
3. `GET /weather/delhi` again — Verify the cache response when the cached entry is still valid.
4. `GET /weather/london` — Test another city.
5. `GET /history` — Verify that request history is stored.
6. `GET /history?limit=5` — Test the history limit.
7. `GET /weather/invalidcityxyz` — Test invalid-city handling.

Use `http://localhost:3000` as the base URL unless you configure a different port.
